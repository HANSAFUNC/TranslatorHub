# 项目固定词库：设计

> 状态：**第 1–7 步已实现**（见 §9）；只剩编辑器里的术语提示没做。
> 文末三个待定项已按本文的倾向实现：项目覆盖组织并写明覆盖了谁、已定稿的违反升 ERROR（发布校验因此自动生效）、
> 第一份词库从已有译文抽候选。

## 0. 结论

该有。而且不需要新建一套东西——`glossary_terms` 表**已经有项目级这一档**（`project_id` 可空，空表示组织级），
QA 里已经有 `GLOSSARY_TERM_MISSING`（默认开启）会按 `case_sensitive` 校验，AI 起草时也会把术语塞进提示词。

真正缺的是三样：

1. **能策展它的地方**——web 端一个字都没有，REST 只能一条条加、不能改不能删，**MCP 里 Agent 根本没有写工具**。
2. **一条词条的身份**——没有唯一约束、没有状态、没有"不要翻译"、没有谁在何时改的。
3. **"固定"靠什么成立**——改了术语，已有译文不会重新查。没有这一条，它只是一份文档。

## 1. 今天已经有什么

| 能力 | 状态 | 落在哪 | 缺什么 |
| --- | --- | --- | --- |
| 词条存储 | 有 | `glossary_terms`：`term` / `translations{locale→值}` / `description` / `caseSensitive`，`projectId` 可空 | 唯一约束、状态、更新人、更新时间 |
| 读取 | 有 | `GET /projects/:id/glossary`；MCP `get_glossary` | 组织级与项目级同名词各返回一条，**没有优先级** |
| 写入 | 半 | `POST /projects/:id/glossary`，一次一条 | 改、删、批量导入都没有；**Agent 没有任何写工具** |
| QA 校验 | 有 | `packages/domain/src/qa.ts` 的 `GLOSSARY_TERM_MISSING`，默认开启，WARNING | 不区分词条是否已定稿——草稿和钦定一样只是警告 |
| AI 起草 | 有 | `packages/domain/src/ai.ts` 把术语对塞进提示词 | 只传 `term→translation`，`caseSensitive` 被丢掉 |
| 界面 | **无** | — | web 端没有入口 |
| 术语改动的影响 | **无** | — | 改了词条，已有译文不会重新检查 |

## 2. 三条界线：一条词条属于谁

"固定"的第一层是：**同一个原文词只可能有一个答案**。

现在两个来源是**并列**的（`OR: [{ projectId }, { projectId: null }]`），谁也没压过谁：组织里一条、项目里又一条，
QA 会照着两条各报一次，两条不一样时没人知道该听谁的。

```
组织级（跨项目的既有说法：公司名、品牌、法务口径）
   ↓ 被覆盖
项目级 · 固定词库（这个产品的词汇表）—— 同名词一律压过组织级
   ↓ 未定义
没有词条 → AI 自由发挥，QA 不管
```

优先级要有地方看得见：接口返回时带上 `scope` 与被压过的另一条，界面上写明"项目词条覆盖了组织词条"，
而不是悄悄取一个。

## 3. 一条词条要有哪些字段

| 字段 | 为什么要它 | 没有它会怎样 |
| --- | --- | --- |
| `term` | 原文词 | — |
| `translations` | 语言 → 译法 | — |
| `caseSensitive` | 是否区分大小写 | 已有，但 AI 那条路把它丢了 |
| `status` **新增** | `DRAFT` / `APPROVED` / `DEPRECATED` | 机器抽出来的候选和人钦定的术语一个分量，表会烂 |
| `doNotTranslate` **新增** | 任何语言都保持原样（产品名、缩写） | 只能给每种语言抄一遍同样的值，加一种语言就漏一个 |
| `forbiddenTargets` **新增** | 明确"不要译成 X" | 最常见的术语库需求，现在无处可写 |
| `updatedAt` / `createdById` **新增** | 谁在什么时候改的 | 固定词库是要担责任的，答不出"谁定的"就不叫固定 |

唯一约束是"固定"的地基：

```sql
CREATE UNIQUE INDEX glossary_project_term_key
  ON glossary_terms (project_id, lower(term))
  WHERE project_id IS NOT NULL;
```

## 4. 词条从哪来

空词库没人愿意开始填。三条路，按见效快慢排：

1. **从已有译文里抽候选**（最有价值）。一个已经翻了 2,791 条 key 的项目，词汇表其实**已经存在**了，只是在译文里。
   按出现频次从原文里抽短语，把现有译法作为建议值，落成 `DRAFT` 词条，等人确认。不猜、不改任何已有译文。
2. **编辑器里随手存**。译者在句子里选中一个词 → 存为术语。这是唯一在"人正好看着这个词"时发生的入口，质量最高。
3. **批量导入**。企业现实：现成的术语表在 Excel、TBX 或某份 `.strings` 里。按 `term` upsert，
   全部落成 `DRAFT` 或直接 `APPROVED`（由导入者指定）。

顺手的一条：**Agent 也能提**。一个 Agent 翻完整个仓库，正是最先发现"这个词每次都译成 X"的人。
给它一个写工具，但只能写 `DRAFT`。

## 5. "固定"靠什么成立

光有一张表不叫固定。五个生效点，缺一个它就是个摆设：

| 生效点 | 今天 | 设计 |
| --- | --- | --- |
| AI 起草 | 术语对进提示词，`caseSensitive` 丢失 | 带大小写规则；`doNotTranslate` 直接锁定；被覆盖的组织词条不再传给模型 |
| QA 校验 | 一律 WARNING | 按状态定严重度：违反 `APPROVED` → **ERROR**；违反 `DRAFT` → WARNING；`DEPRECATED` 不参与 |
| 编辑器 | — | 原文出现该词时旁边显示"术语：课程 → Course"，一键插入；违反就地标红 |
| 发布校验（`validate_release`） | **当时不会挡**：它自己重算缺译/占位符/过期/冲突，从不读术语库 | 术语违规升成 ERROR，并由发布前校验自己问一遍术语库（2026-11-20 补上，见 §9） |
| **术语改动** | **什么都不发生** | 改一条词条 = 一个事件：把"原文含这个词"的条目重新排一次 QA。平台已有 STALE 机制处理源文变更，这是同一形状的事件 |

最后一行是这份设计的重点。词库的价值在于**改了之后全项目跟着收敛**；如果改词条只影响下一次翻译，
那它只是一份文档，不是约束。

## 6. 接口面

| 面 | 要有的东西 |
| --- | --- |
| REST | `GET` 带 `scope` 与覆盖信息；`PATCH /glossary/:id`、`DELETE`、`POST /glossary/import`（按 term upsert）、`POST /glossary/extract`（抽候选） |
| MCP | `get_glossary`（读）、`extract_glossary_candidates`（读，需 `glossary.read`）、`upsert_glossary_terms`（写单条/少量，只能 DRAFT）、`import_glossary_terms`（导入整份词表，`status` 默认 DRAFT，APPROVED 需 PROJECT_MANAGER） |
| Web | 项目页 `/projects/[id]/glossary`：词条表（原文、逐语言译法、状态、谁在何时改的）+ 候选队列 + 导入 |
| 权限 | 已经有 `glossary.read`；补 `glossary.write`。审核者能改状态，译者只能提候选 |

## 7. 动手顺序

按"先让它成立，再让它好用"排；每一步都能独立上线。

1. **模型补齐**：唯一索引 + `status` + `doNotTranslate` + `forbiddenTargets` + 审计字段（一次迁移）。
2. **优先级与去重**：三个读点（API / worker / QA）统一走一个解析函数，项目压组织；顺手修掉"同名词报两次"。
3. **能被策展**：REST 的 PATCH / DELETE / import，加 MCP 的 `upsert_glossary_terms`——让有知识的人（人和 Agent）能把它写进来。
4. **严重度分级**：`APPROVED` 违反升 ERROR，发布校验自动生效。
5. **改动触发重查**：词条变更入队，重跑相关条目的 QA。到这一步"固定"才真的成立。
6. **界面**：项目词库页 + 编辑器里的术语提示。
7. **抽候选**：从已有译文里长出一份草稿词库。

## 8. 待定三项

1. **组织级词条被项目覆盖时，是静默覆盖还是提示？**
   倾向：项目赢，但接口和界面都写明"这条覆盖了组织词条 X"，并且允许项目里显式禁用某条组织词条
   （`disabled: true`），而不是必须写一条同名词去压它。
2. **违反已定稿术语，该不该挡住发布？**
   倾向挡。否则"固定"只是建议，而建议在赶工期时第一个被牺牲。真需要放行的情况，走一次带备注的例外审批，留下记录。
3. **第一份词库从哪来——导入现成的表，还是从已有译文抽？**
   这决定先做第 7 步还是第 6 步。手里已经有术语表（Excel/TBX）就先做导入；没有的话抽候选见效最快，因为它不需要谁去填。

### 重查是怎么触发的

`recheckAfterGlossaryChange`（`apps/api/src/modules/misc/content.controller.ts`）与 MCP 的
`enqueueQaRecheck`（`apps/mcp-remote/src/qa-queue.ts`）做同一件事：把一次全项目 QA 运行排进 `qa` 队列。

三个刻意的选择：

- **跑整个项目，不挑条目。** 设计里写的是「把原文含这个词的条目重排一次」，实现时改成整项目重跑：挑条目要先扫一遍全项目的原文
  才知道挑哪些，而重跑本来就只发生一次、算完的结论一样。等真有人抱怨大项目上慢，再按词筛。
- **入队失败不抛错。** 术语已经写进去了；Redis 抖一下就把一次成功的保存变成 500，是在对使用者说谎。
  `recheck.queued` 会如实告诉调用方排没排上，页面据此换一句提示（「已定稿，但重查没排上——请手动跑一次 QA」）。
- **一个项目一个 jobId + `removeOnComplete`。** 导入一次、再改一条，合并成一次运行；跑完 id 立刻释放，
  否则下一次改动会被当成重复任务丢掉。


### 抽候选后来加上了译法（2026-11-20）

第一版只给「词汇的形状」：哪些短语反复出现、出现在多少条 key 里、举例——理由是「一句原文和它的译文对不出其中某一个词变成了什么」。
这个理由本身没错，但它推不出「什么都不给」：一个已经翻了 2,795 条的项目，早就把词库的大半答案写在自己的译文里了
（`学习 → 學習` 152 条、`课程 → 課程` 116 条、`选择 → 選擇` 105 条）。**数出来不是猜出来**，所以现在每条候选带着：

- **每个语言的建议值**，以及支撑它的计数：`コース 3/4` 说的是"这几条里 3 条这么写"，不是"平台认为应该这么写"；
- **一个完整例子**（原文 → 译文）。计数可以对着错的东西数对——某个词只是**老出现在术语旁边**而不是它的译法——
  例子是让人两秒钟就能看出来的那一眼；
- 加入后仍是 **DRAFT**，而且表格里每一格译法都能点开就地改（一条改不动的建议比没有建议更糟）。

三类错误是明确拒绝的，都在 `packages/domain/src/term-mining.ts` 里有名字、有测试：

| 计数会错的地方 | 真实例子 | 拒绝的理由 |
| --- | --- | --- |
| 原文的边界就切错了 | `ID` 在项目里只出现在 `IDA标签` 里，计数说 `ID → IDA` 95/109 | 拉丁术语必须在译文里**成词**出现；只是被粘进更长的词，说明术语本身切错了 |
| 把零件当词汇 | `%@`、`\n`、`{{count}}`、纯数字在 strings 文件里和真词一样高频 | 术语本身是机器文本就不找译法；候选值里的机器文本也不算数 |
| 窗口切在词中间 | `ース` 和 `コース` 在三句译文里计数完全相同 | 日语片假名/韩文是分词书写的：一个从不成词出现的窗口不是词（中文没有这条——`課程學習` 中间没有空格，粘着不代表什么） |

另外两条是统计本身的要求：出现次数少于 2 条不给建议；覆盖率低于一半不给建议；
某个说法在**不含该术语**的键里也普遍出现（背景率 > 20%）就淘汰——没有这一条，`的` 和 `Please` 会赢下每一次计数。

**仍然做不到的**：它数的是「和术语共现」，不是对齐。`填写` 的英文建议是 `Please`（44/76）——因为含"填写"的句子多数以"Please"开头。
计数、例子、语言标签都摆在那一行上，人一眼能判断；平台不替人下结论，但也不再让人从零开始默写。

### 实现时改掉的两处判断

- **`status` 默认 DRAFT。** 设计里没写默认值，实现时选了 `DRAFT`：既有词条和新词条都先是草稿，
  QA 对它们的行为与今天完全一致（警告）。**升级一条违规为错误必须是某个人的决定，不能是迁移的决定**——
  否则一次迁移就会让某个项目的发布闸门突然关上。
- ~~**抽候选不猜译法。**~~ **这条后来被推翻了**（见上一节）：设计里本来写的就是"把现有译法作为建议值"，
  实现时我按"对不出就不给"去掉了，但那是把「不能对齐」当成了「不能计数」。现在给的是计数出来的值 + 例子 + 草稿状态，
  该拒绝的三类错误在 `term-mining.ts` 里有名字有测试。

### 一处漏掉的假设（2026-11-20 补）

§5 那张表里「发布校验」一行原本写着「不用改：QA 问题已经会挡发布」。**这个前提是错的**，而且是写完文档、
写完状态页之后才被读代码推翻的：`validateForRelease`（`validate_release` / `POST /projects/:id/sync/validate`）
自己重算缺译、占位符、过期、开放冲突四类问题，从不读 `qa_issues`，也从不读术语库。所以在一段时间里，平台同时
说两件相反的话：QA 页面上 `课程 → Course` 是红色 ERROR，而发布前校验对同一个项目回 `ok: true`。

现在由发布前校验自己问一遍术语库，用的是 QA 那份 `glossaryFindings`（同一函数，不可能两处不一致）。
草稿词条的违规会出现在报告的 `issues` 里但不阻断（`ok` 只看 ERROR），定稿的会阻断。

**仍然没做的一步**：`POST /projects/:id/releases`（真正建 release）本身不调用发布前校验，所以「挡」目前发生在
校验这一步，而不是建 release 那一步。要在那一步也挡住，需要先有设计里提到的那条「带备注的例外」路径，
否则就是一道没有出口的墙。

### 已知的两处不完整

- `disabled`（项目里关掉某条组织词条）与 `forbiddenTargets`（不要译成 X）**接口支持（含 MCP），后台管理界面还没有编辑入口**。
- 源文短语按出现频次抽（CJK 2–5 字、拉丁 1–3 词的重叠窗口），用"更长的包含它且不更少见"过滤掉碎片；
  译法由 `term-mining.ts` 从现有译文里数出来（背景最多取 300 条、共现最多取 200 条，计数按取样后的集合算，
  所以 `152/152` 是真实数出来的比例，不是外推）。
  对合成的规模测试数据（`after 0`、`after 1`…）只会抽出 `after` 一个——那是数据的问题，不是提取器的问题。
